# Altrone v4 — заметки по рефакторингу архитектуры

> Дата сессии: 2026-08-04
> Статус: **обсуждение теории, ничего не реализовано**. Это конспект архитектурного разговора,
> не техническое задание — перед реализацией каждый пункт нужно будет проработать в план.

---

## 1. Видение

Altrone остаётся библиотекой компонентов, но переходит от "собери экран вручную из примитивов"
к "опиши экран через `Application`/`Screen`". Явно **не** DSL/schema-driven фреймворк (эта идея
была отклонена в начале обсуждения) — просто более чёткое разделение приложения на экраны через
компоненты.

---

## 2. Application / Screen

- **`AltroneApplication`** становится чистым корнем-провайдером: тема, локаль, конфиг, диалоги,
  тосты. Больше **не** рендерит `Screen` внутри себя и **не** владеет пропами `sidebar`/`header` —
  это breaking change (сейчас `AltroneApplication` рендерит `<Screen>` в корне, см.
  `AltroneApplication.tsx`).
- **`Screen`** — компонент, который потребитель кладёт внутрь `children` приложения (один или
  несколько). Переключение между экранами (какой активен) — не забота библиотеки, а забота
  потребителя (свой роутер/state).
- API `Screen` переходит с текущих пропов `header`/`sidebar` на namespace-зоны:
  `Screen.Header`, `Screen.Sidebar`, `Screen.Content`, `Screen.Footer`.
- У `Screen` появляется проп `size` (`mini/s/m/l/xl`) — ограничение ширины контента.
- Текущий `Screen.tsx` уже использует правильные семантические теги (`<aside>`, `<header>`,
  `<main>`) — сохранить это в новой версии.
- **Пресеты Screen — решено делать сабкомпонентами** (реальный код в библиотеке, не только
  рецепты в Storybook): `Screen.ListDetail`, `Screen.Dashboard`, `Screen.Form`, `Screen.Settings`,
  `Screen.DataView`, `Screen.Auth`, `Screen.Empty`.

## 3. Box — универсальный примитив

Назначение: общий визуальный примитив для "чиповых" компонентов (Button, Input, Badge, Tag,
Avatar, Card, Chip и т.п.). **Не** для структурно сложных компонентов (Splitter, Tabs, DataGrid,
Range) — те используют Box точечно для отдельных внутренних частей (например,
`Splitter.Divider`), а не целиком.

### Пропы (черновик)

```ts
interface BoxProps {
  shape?: 'square' | 'rounded' | 'capsule' | 'circle';
  material?: 'solid' | 'glass' | 'translucent' | 'transparent' | 'outline' | 'ghost';
  tone?: 'neutral' | 'accent' | 'danger' | 'success' | 'warning'; // + возможно 'info'
  size?: 'mini' | 's' | 'm' | 'l' | 'xl';
  elevation?: 'flat' | 'raised' | 'sticky' | 'overlay' | 'modal' | 'toast';
  pressable?: boolean;
  focusable?: boolean;
  editable?: boolean;
  asChild?: boolean;
  ref?: Ref<HTMLElement>;
}
```

### Ключевое ограничение — SSR

**Box обязан быть SSR-safe и не должен иметь собственного React state.** Взаимодействия
(`pressable`/`focusable`/`editable`) реализуются только через чистые CSS-псевдоклассы
(`:active`, `:focus-visible`, `:focus-within`), никогда через JS state — иначе вся библиотека
каскадно уходит в `'use client'`, так как Box лежит в основе почти всех компонентов.

### Поведение взаимодействий

- **`pressable`** — для кнопок реализуется через изменение яркости фона (не через JS
  state-layer/wash). Работает естественно со стеклом/полупрозрачностью, так как там уже есть
  альфа-канал, который можно затемнить/осветлить.
- **`focusable`** — всегда одинаковое `:focus-visible`-кольцо, независимо от материала —
  предсказуемость для screen-reader пользователей важнее визуальной кастомизации.
- **`editable`** — режим для `asChild` над `<input>`/`<textarea>`: триггер взаимодействия
  переключается с hover/active на `:focus-within`, чтобы во время печати hover-стили не
  конфликтовали с активным состоянием.
- **Полиморфизм** — только `asChild` (Radix Slot паттерн), без отдельного пропа `as`.

### Материалы — таблица поведения

| Материал | Заливка в покое | Блюр | Граница | Поведение при `pressable` |
|---|---|---|---|---|
| `solid` | 100% непрозрачная | — | — | темнее/светлее по тону |
| `translucent` | полупрозрачная | нет | — | увеличение alpha |
| `glass` | полупрозрачная | есть (`backdrop-filter`) | — | сдвиг alpha/saturate, а не цвета |
| `transparent` | нет | — | нет | временно получает translucent-заливку |
| `outline` | нет | — | есть, статична | заливка/усиление границы |
| `ghost` | нет | — | появляется при взаимодействии | временно получает translucent-заливку |

## 4. Скругления — формула "concentric radius"

- Формула: `radius_child = radius_parent - gap`, с клампом в 0 (`max(0px, ...)`), если `gap ≥
  radius_parent`.
- Прецеденты: shadcn/ui (все тиры `--radius` считаются через `calc()` от одного корневого
  значения), Apple SwiftUI `ContainerRelativeShape` (дочерний элемент запрашивает форму
  контейнера динамически).
- **Решение: реализовать через CSS `calc()` от унаследованных custom properties**
  (`var(--radius-outer)`, `var(--space-outer)`), а не авторить параллельную статичную таблицу
  радиусов по размерам — иначе получаем тот же рассинхрон source-of-truth, который сейчас чиним
  в spacing.
- Наследование CSS custom properties — веб-эквивалент Apple `ContainerRelativeShape`: дочерний
  элемент читает `var(--radius)` родителя через каскад, без единой строчки JS, дёшево по
  производительности (resolve на этапе style recalculation).
- Для анимируемости радиуса при transition — регистрировать через CSS Houdini `@property`
  (`syntax: '<length>'`), иначе plain custom property анимируется как строка (дискретно).

## 5. Spacing — семантические роли

**Проблема (найдена в коде):** в проекте уже есть готовая семантическая шкала (`--narrow-gap`,
`--xs-gap`, `--s-gap`, `--gap`, `--l-gap`, `--xl-gap`, `--xxl-gap` в
`altroneApplication.module.scss`), но она не используется — ~100+ мест в компонентах хардкодят
px напрямую.

- **Решение:** отступы — отдельная от `size` сущность (не переиспользовать словарь
  `mini/s/m/l/xl` для spacing).
- Роли называются по **назначению**, не по величине.
- `6px` у текущего `--s-gap` ломает 4px-сетку — решено привести к 4px (снапнуть, скорее всего
  до 8px, либо убрать тир).
- Черновик ролей (принято "скорее да", не финализировано):
  - `--space-control-x` / `--space-control-y` — внутренний паддинг контролов
  - `--space-inline` — зазор иконка↔текст
  - `--space-stack` — вертикальный ритм между полями/пунктами списка
  - `--space-content` — паддинг внутри контентных контейнеров
  - `--space-section` — зазор между крупными блоками layout
  - `--space-inset-compact` — плотные списки/таблицы
- **Важный нюанс:** control-роли должны варьироваться по `size` компонента (mini/s/m/l/xl) — то
  есть это матрица роль × size, не плоские значения — потому что от них зависит ещё и радиус
  (формула из раздела 4).

## 6. Типографика — ОТЛОЖЕНО, вернуться позже

- Существующие примитивы (`_text.scss`): `--text-size-1..9`, `--line-height-1..9` (имена
  корректны, не переименовывать), `--text-weight-*` — всё в **px**.
- Черновик content-ролей (не подтверждено): `title` / `subtitle` / `body` / `caption` / `code`
  + кандидаты `display` / `overline` / `legal` / `link` / `numeric` (`tabular-nums`, особенно
  полезно для DataGrid/DataTable/NumberInput).
- Черновик control-ролей: `--text-control-{mini,s,m,l,xl}`, привязаны 1:1 к `size` компонента
  (здесь, в отличие от spacing, переиспользование словаря size было принято — текст физически
  является частью размера компонента).
- **Иконки:** библиотека остаётся lucide-react (не менять). **Размер иконки должен быть привязан
  к `size` компонента** (подтверждено). Идея на будущее (не решено): толщина обводки иконки
  (`strokeWidth`) может следовать за `--text-weight` того же tier — по аналогии с тем, как
  SF Symbols синхронизирует начертание иконки с начертанием текста рядом.
- **`rem` для типографики — отклонено, пока не переходим.** Зафиксировать как известный
  пробел: HIG-эквивалент (Dynamic Type) на вебе — это `rem`-based шкала вместо px, иначе
  пользовательская настройка размера текста в браузере/ОС не работает. Не реализуем сейчас,
  но помним об этом.

## 7. Elevation — z-index + тень в одной семантической роли

- **Z-index уже полностью готов** (`altroneApplication.module.scss`, Bootstrap-style):
  `--level-dropdown(1000) → sticky(1020) → fixed(1030) → offcanvas-backdrop(1040) →
  offcanvas(1045) → modal-backdrop(1050) → modal(1055) → popover(1070) → tooltip(1080) →
  toast(1090)`.
- **Тени тоже готовы** (`_shadow.scss`, рецепт в духе Radix Colors): `--shadow-none`,
  `--shadow-inset`, `--shadow-1..5`.
- **Найденная дыра:** у `--shadow-*` нет dark-theme override вообще — тени построены на
  `--black-aN`, на тёмной поверхности почти не видны. Нужно решение в духе Material 3 (tonal
  elevation — высота через подмешивание тона в поверхность, а не только через shadow). Детали
  не проработаны.
- **Решение (подтверждено, нравится):** связать z-index и тень в одну семантическую роль:

  | Роль | z-index | Тень (light) | Кандидаты |
  |---|---|---|---|
  | `--elevation-flat` | auto | `--shadow-none` | Box в покое |
  | `--elevation-raised` | auto / `--level-dropdown` | `--shadow-1`+`--shadow-2` | Tabs item, DatePicker day |
  | `--elevation-sticky` | `--level-sticky` | лёгкая нижняя грань | Screen.Header, DataTable columnHeaders |
  | `--elevation-overlay` | `--level-popover` | `--shadow-1`+`--shadow-4` | Popover, Dropdown, Drawer |
  | `--elevation-modal` | `--level-modal` | `--shadow-1`+`--shadow-5` | Modal, Dialog |
  | `--elevation-toast` | `--level-toast` | `--shadow-1`+`--shadow-5` (или новый `--shadow-6`) | Toast |

- **Найдена нестыковка:** `NavigationList`/`BottomNavigation` сейчас используют `shadow-1`+
  `shadow-5` (вес уровня Modal), хотя это постоянный chrome, а не оверлей — вероятно, стоит
  понизить до `--elevation-raised`. Не подтверждено окончательно.

## 8. Цветовая система

- **Уже отлично:** полные Radix Colors палитры (12 ступеней + alpha `aN`, P3) для 8 accent-хью
  (red/pink/purple/indigo/blue/teal/amber/brown) + gray + black. Индирекция через
  `[data-altrone-accent='X'] { --accent-N: var(--X-N); }` уже реализована правильно —
  компоненты ссылаются на `--accent-N`, не на сырые имена хью.
- **Найденная дыра:** `danger`/`success`/`warning` — плоские одиночные цвета (`_common.scss`),
  не полноценные 12-ступенчатые шкалы. Зелёной палитры для `success` не существует вообще.
- **Решение:** завести полноценные семантические токены для типов сообщений — но **не** сырые
  `danger-1`/`danger-2` напрямую потребителю, а именованный по смыслу слой поверх шкалы (по
  аналогии с подходом spacing/radius: примитив + семантический алиас). Точные имена не выбраны.
- **Открыто:** `danger/success/warning` (+ возможный 4-й статус `info` для нейтральных
  информационных сообщений) — фиксированные хью независимо от выбранного `accent`, или тоже
  переключаемые? Рекомендация (по конвенции Radix Themes) — фиксированные, чтобы `accent="red"`
  не сливался визуально с `danger`. Не подтверждено окончательно.
- **Категориальная (qualitative) палитра** — для `Avatar` (цвет фона под инициалы), `Tags`/
  `Badge` (выбор цвета метки), `Calendar` (категории событий). Отдельная задача от 12-ступенчатой
  шкалы — нужен фиксированный набор ~8–12 самостоятельных, взаимно различимых цветов, не
  оттенков одного тона. **Решение не принято** — обсуждение прервалось, вернуться к вопросу
  (сколько цветов, авто-подбор по хэшу имени или ручной проп у компонента).
- **Disabled — решено делать отдельной цветовой палитрой, не через opacity.** Прозрачность
  непредсказуема поверх glass/translucent материалов (альфа-каналы складываются) — нужна
  выделенная приглушённая палитра для заблокированных элементов.
- **`forced-colors` (Windows High Contrast Mode)** — поднято как реальный accessibility-пробел,
  явно отложено ("опустим этот вопрос") — не забыть вернуться.
- **Точечные токены** (не шкала, один цвет под одну задачу): `--focus-color` уже есть.
  Нужны/стоит проверить: `--color-overlay-scrim` (затемнение фона под Modal/Drawer — возможно,
  сейчас захардкожен rgba), `--color-selection`. Открытый вопрос: `Screen.HeaderBackdrop`
  сейчас использует `--accent-a3` для подложки — акцентный тон осознанно, или должен быть
  нейтральным `--gray-a3`?
- Числовые дельты (+/− в DataGrid/DataTable) должны переиспользовать `success`/`danger` +
  `--text-numeric`, отдельный токен не нужен.

## 9. Motion / reduced motion

Три слоя реализации (план, не реализовано):

1. **Чистый CSS** — длительности/easing как CSS custom properties
   (`--motion-duration-fast/base`, `--motion-easing-standard`), обнуляются под
   `@media (prefers-reduced-motion: reduce)` на корне — один источник правды.
2. **JS-анимации через `motion`** (уже в зависимостях, v12, используется в Button/DataTable/
   DatePicker) — обернуть дерево провайдеров `AltroneApplication` в
   `<MotionConfig reducedMotion="user">` для глобального эффекта без правки каждого компонента.
3. **Ручной JS-тайминг** (например, `setTimeout` перед unmount после exit-анимации) —
   переиспользовать уже существующий SSR-safe `useMediaMatch('(prefers-reduced-motion: reduce)')`
   вместо хардкода длительностей.

Нюанс (WCAG 2.3.3): reduced motion ≠ убрать всё движение. Прямая обратная связь на действие
(`Splitter.Divider` за курсором) не убирается — убирается декоративное/автоплей/зацикленное
движение (например, `Skeleton` shimmer → статичное/пульсирующее состояние).

Не решено: оформлять ли это как раздел `## Motion & reduced motion` в `CLAUDE.md`.

## 10. Тёмная тема

- Текущий подход (JS-state → data-атрибут, не полагаться только на `prefers-color-scheme`)
  принципиально верный, совпадает с конвенцией next-themes/Radix Themes.
- **Найдено:** два параллельных селектора — `[data-altrone-theme='dark']` (актуальный, в
  цветовых файлах) и legacy-класс `.AltroneDark` на `<html>` с мёртвым CSS-блоком на старых
  именах переменных (уже зафиксировано в `application/ROADMAP.md` как техдолг — убрать класс,
  оставить только атрибут).
- Два предложенных улучшения (не решено):
  1. **FOUC при SSR** — добавить инлайновый blocking-скрипт (как у next-themes), выставляющий
     атрибут темы до первого paint/гидратации, раз `AltroneApplication` недавно дорабатывался
     под SSR.
  2. Рассмотреть нативный CSS `light-dark()` + `color-scheme` вместо дублирования каждого цвета
     под `[data-altrone-theme='dark']` в каждом файле хью — отдельная тема, не проработана
     глубоко.

## 11. Адаптивность

- **Двухуровневая модель (подтверждено, "только за"):**
  - viewport breakpoints (`--breakpoint-*`, идея `useBreakpoint()` из `application/ROADMAP.md`)
    — для решений уровня приложения (показывать ли мобильную навигацию).
  - container queries (`@container`) — для компонентного уровня (Screen внутри Splitter-панели,
    карточки) — переход "местами", не везде.
- **Визуальная vs структурная адаптивность:** визуальная (спрятать элемент, поменять grid) —
  чистый CSS `@container`, без JS, без риска SSR-рассинхрона. Структурная (List-Detail
  схлопывается в одну панель) требует JS (`ResizeObserver`) — та же проблема
  SSR-рассинхрона, что и с темой/reduced-motion. Предложено (не реализовано): новый
  `useContainerQuery()`/`useElementSize()` хук, SSR-safe, по аналогии с `useMediaMatch`.
- `size` остаётся explicit/авторским пропом, не должен неявно меняться по брейкпоинту —
  соответствует философии проекта (explicit config, не магия).
- HIG-инсайт: адаптивность — это не просто resize, а смена *идиомы* навигации (tab bar ↔
  sidebar) — относится к пресетам Screen/List-Detail.

---

## 12. Density/compact-режим — отклонено

Глобальная пользовательская настройка плотности (отдельная от `size`, как в Ant compact-теме,
Salesforce Lightning, Airtable row height) — **решено, что пока не нужна**. У Altrone нет
выраженного data-dense сценария использования, который бы это оправдывал; `size` уже покрывает
реальные потребности.

---

## 13. Accessibility — общие заметки

- Клавиатурная навигация: roving tabindex в composite-виджетах, стрелки, `Escape` закрывает
  оверлей и возвращает фокус на триггер, `Home`/`End`.
- Фокус: `:focus-visible` (не `:focus`), focus trap в Modal/Dialog/Drawer, возврат фокуса при
  закрытии.
- Семантика сначала нативная, ARIA — только когда нет нативного эквивалента.
- Иконка-only контрол обязан иметь `aria-label` (паттерн `Toolbar.Action` уже есть — закрепить
  как обязательное правило, не опцию).
- `aria-live` для Toast.
- Контраст: WCAG AA 4.5:1 текст / 3:1 крупный текст и UI-элементы; состояние никогда не только
  цветом.
- `prefers-reduced-motion` — см. раздел 9.
- Хит-зона ≥ ~24px даже при `size="mini"`.
- `aria-invalid` + `aria-describedby` для валидации форм.
- `forced-colors` — см. раздел 8, отложено.
- Не решено: оформлять ли раздел `## Accessibility` в `CLAUDE.md`.

---

## 14. Отклонённые идеи

- **DSL/schema-driven экраны** — отклонено в начале обсуждения, слишком далеко от желаемого;
  скоуп — просто композиция через Application/Screen.
- **Монорепозиторий** для тяжёлых компонентов (DataTable/ColorPicker/DataGrid) — отклонено:
  релизы синхронны и всё сильно связано, ESM tree-shaking уже решает вопрос размера бандла без
  тулинг-нагрузки монорепо.
- **Density/compact-режим** — отклонено, нет чёткого кейса (см. раздел 12).
- **`rem` для типографики** — отклонено пока, зафиксировано как известный пробел на будущее
  (см. раздел 6).
